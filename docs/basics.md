# RU-Vibe 기초 — 완전 처음부터

이 문서는 "버킷이 뭔지도 모르겠다"에서 출발한다. 아는 걸 전제하지 않는다.
읽는 순서대로 쌓이게 썼으니까 위에서부터 차례로 보면 된다.

각 개념은 항상 같은 순서로 설명한다:
**(1) 이게 없으면 뭐가 불편한가 → (2) 그래서 이건 뭔가 → (3) 우리 앱 어디에 있나**

---

# 0. 30초 요약

우리가 만든 것은 **웹사이트**다. 앱스토어에서 받는 앱이 아니라, 사파리로 주소를 치면 열리는 것.

```
학생 폰 (사파리)  ←→  인터넷 어딘가의 컴퓨터들
```

인터넷 어딘가의 컴퓨터가 **두 종류**다.

1. **Next 서버** — 우리가 짠 코드가 도는 곳. 화면(HTML)을 만들어 보내준다
2. **Supabase** — 남이 만들어 파는 "뒷마당 세트". 로그인 + 데이터베이스 + 파일창고 + 실시간알림이 한 덩어리

그리고 이 프로젝트의 핵심 한 문장:

> **학생 폰은 Next 서버를 건너뛰고 Supabase와 직접 이야기한다.**

사진을 올릴 때도, 지도에 찍을 핀 목록을 가져올 때도, 우리 서버는 관여하지 않는다.
그래서 **"누가 뭘 해도 되는지"를 판단하는 규칙이 Supabase 안에 있어야 한다.** 우리 서버에 두면 그냥 안 거치고 지나가 버리니까.

이 문장이 README 첫 문단이고, 면접에서 이 프로젝트를 설명할 때 첫 문장이다.

---

# 1. 웹이 뭔지부터

## 1-1. 서버 = 항상 켜져 있는 남의 컴퓨터

**없으면 뭐가 불편한가.**
네가 만든 웹사이트 파일이 네 노트북에만 있으면, 친구가 보려면 네 노트북이 켜져 있고 인터넷에 연결돼 있어야 한다. 네가 노트북을 닫으면 사이트가 사라진다.

**그래서 서버는 뭔가.**
**24시간 켜져 있고 인터넷에 붙어 있는 컴퓨터.** 특별한 기계가 아니다. 그냥 "꺼지지 않는 컴퓨터"다. 누가 요청하면 파일을 보내주는 일만 계속 한다.

**우리 앱에서는.**
Vercel이라는 회사가 서버를 빌려준다. 우리가 `git push`하면 Vercel이 우리 코드를 받아서 자기 서버에 올리고, 그때부터 `ru-vibe.vercel.app` 주소로 누구나 접속할 수 있다.

## 1-2. 클라이언트 = 부탁하는 쪽

**클라이언트(client)** = 요청하는 쪽. 우리 경우엔 **학생의 사파리**.
**서버(server)** = 답해주는 쪽.

식당으로 치면 손님이 클라이언트, 주방이 서버다. 손님이 주문(요청)하고 주방이 음식(응답)을 준다.

중요한 건 **이 둘이 서로 다른 컴퓨터**라는 것. 이게 웹 개발의 거의 모든 헷갈림의 뿌리다.

- 서버에는 **카메라가 없다**. GPS도 없다. 화면도 없다
- 브라우저에는 **데이터베이스 비밀번호가 없다**(있으면 안 된다)

## 1-3. 요청 = 편지

주소창에 `ru-vibe.vercel.app/map`을 치면, 브라우저가 서버에 **편지 한 통**을 보낸다. 실제로 이렇게 생겼다:

```
GET /map HTTP/1.1              ← 뭘 달라는지
Host: ru-vibe.vercel.app       ┐
User-Agent: Mozilla/5.0 ...    │  헤더 = 봉투에 적힌 정보
Cookie: sb-xxxx-auth-token=... ┘
                               ← 빈 줄
(내용물 — GET에는 보통 없음)
```

**헤더(header)** = 요청 맨 앞에 붙는 `이름: 값` 목록. **브라우저가 자동으로 채운다.**

이걸 눈으로 본 적 있다: 개발자도구 → Network → `map` 클릭 → Request Headers.

서버는 답장을 보낸다:

```
HTTP/1.1 200 OK
Content-Type: text/html

<html>...</html>
```

**상태 코드(status code)** — 답장 맨 앞의 숫자. 이 프로젝트에서 만난 것들:

| 숫자 | 뜻 | 우리가 만난 곳 |
|---|---|---|
| 200 | 됐다 | 거의 모든 정상 응답 |
| 307 | "다른 데로 가라" | `proxy.ts`가 비로그인을 `/login`으로 보낼 때 |
| 400 | "요청이 이상하다" | 새 키를 `Authorization`에 잘못 넣었을 때 |
| 401/403 | "너 그럴 권한 없다" | Mapbox가 남의 사이트 요청을 거절할 때 |
| 404 | "그런 거 없다" | 없는 파일을 옮기라고 했을 때 |

# 2. 장소 3개 — 이 프로젝트의 지도

앞으로 나오는 모든 이야기는 이 셋 중 어디서 벌어지는가로 정리된다.

```
┌──────────────┐      ┌──────────────┐      ┌─────────────────────┐
│  ① 브라우저   │      │  ② Next 서버 │      │  ③ Supabase         │
│  (학생 폰)    │      │  (우리 코드)  │      │  (뒷마당 세트)       │
├──────────────┤      ├──────────────┤      ├─────────────────────┤
│ 카메라       │      │ HTML 만들기   │      │ 로그인 관리          │
│ GPS          │      │ proxy.ts     │      │ 데이터베이스          │
│ 지도 그리기   │      │ (로그인 문지기)│      │ 파일 창고            │
│ 캔버스       │      │              │      │ 실시간 알림          │
└──────┬───────┘      └──────────────┘      └──────────▲──────────┘
       │                                                │
       └────────────────────────────────────────────────┘
              사진 업로드 · 핀 조회 · 실시간 연결은
              ②를 건너뛰고 ①↔③ 직통
```

**왜 이게 중요한가.**

만약 ①이 항상 ②를 거쳐야 한다면, 우리 서버 코드에 `if (로그인했나) { 허락 }` 이라고 쓰면 끝난다. 그런데 ①은 ②를 건너뛸 수 있다. 학생이 개발자도구를 열고 Supabase에 직접 요청을 보내면 우리 서버 코드는 **한 줄도 실행되지 않는다.**

그래서 방어선이 ③ 안에 있어야 한다. 이게 뒤에 나올 **RLS**다.

# 3. ② Next 서버가 하는 일

## 3-1. HTML을 만들어 보낸다

**HTML** = 화면의 뼈대를 적은 글자. 이런 것:

```html
<h1>Capture</h1>
<button>Take photo</button>
```

브라우저는 이 글자를 읽고 화면에 제목과 버튼을 그린다.

**없으면 뭐가 불편한가.**
HTML을 손으로 다 적으면, 핀이 50개일 때 `<div>`를 50번 복사해 붙여야 한다. 하나 늘어나면 또 고쳐야 한다.

**그래서 React가 뭔가.**
"데이터를 주면 HTML을 만들어내는 규칙"을 쓰게 해주는 도구. `posts.map(post => <핀 post={post}/>)` 라고 쓰면 데이터 개수만큼 알아서 만든다.

**Next.js는 뭔가.**
React를 쓰는 웹사이트를 만들 때 필요한 잡일(주소별 페이지 나누기, 서버 돌리기, 빌드하기)을 다 해주는 세트. 우리가 `app/(main)/map/page.tsx` 라는 파일을 만들면 Next가 알아서 `/map` 주소에 연결해준다. **파일 위치가 곧 주소다.**

## 3-2. 서버 컴포넌트 vs 클라이언트 컴포넌트

**없으면 뭐가  불편한가.**
Next는 기본적으로 페이지를 **서버에서 실행해서 HTML만 만들어 보낸다.** 이게 빠르다(브라우저가 할 일이 적다). 그런데 서버에는 카메라도 GPS도 없고,"버튼을 누르면"이라는 개념도 없다. 서버는 HTML을 한 번 뱉고 끝이니까.

**그래서 `"use client"`가 뭔가.**
파일 맨 위에 이 한 줄을 적으면 "이 파일 코드는 **브라우저에서도** 실행해라"는 뜻이 된다.

```tsx
"use client";   // ← app/(main)/capture/page.tsx 맨 첫 줄
```

이게 없으면 `useState`, 카메라, GPS를 쓰는 순간 에러가 난다.

**헷갈리기 쉬운 것**: `"use client"`를 붙여도 **첫 HTML은 여전히 서버가 만든다.** 브라우저는 그 HTML을 받아서 화면에 먼저 그리고, 그다음에 자바스크립트를 실행해 "살아 있게" 만든다.

## 3-3. 하이드레이션(hydration)

서버가 만든 HTML은 **그림**이다. 버튼이 그려져 있지만 눌러도 아무 일이 없다. 브라우저가 자바스크립트를 실행해서 그 그림에 동작을 붙이는 과정이 **하이드레이션**(물 주기).

**여기서 중요한 규칙**: 서버가 그린 것과 브라우저가 그리려는 것이 **다르면 React가 화면을 통째로 버리고 다시 그린다.**

우리가 이걸로 실제로 걸린 적이 있다:

```tsx
// 이렇게 쓰면 안 된다
const inApp = /Instagram/.test(navigator.userAgent);
```

서버에는 `navigator`가 없다 → 서버는 항상 false로 그림 → 브라우저는 true일 수도 → 어긋남.

그래서 이렇게 쓴다:

```tsx
const [inApp, setInApp] = useState(false);
useEffect(() => setInApp(isInAppBrowser()), []);  // 하이드레이션 끝난 뒤 실행
```

`components/InAppBrowserBanner.tsx`, `components/InstallPrompt.tsx`가 전부 이 모양이다.

## 3-4. `proxy.ts` — 문지기

**없으면 뭐가 불편한가.**
로그인 안 한 학생이 `/capture`에 들어와서, 사진을 찍고, 위치 권한을 허용하고, 측위를 몇 초 기다린 다음 Post를 눌러야 비로소 "로그인하세요"를 듣는다. 게다가 `/login`으로 이동하는 순간 방금 찍은 사진이 **날아간다**(브라우저 메모리에만 있으니까).

**그래서 이건 뭔가.**
요청이 페이지에 **닿기 전에** 서버에서 먼저 실행되는 코드.

```
브라우저 → [proxy.ts] → 페이지
                ↓
           아니면 /login으로 307
```

**중요**: 이건 **보안이 아니라 UX다.** 개발자도구로 Supabase를 직접 부르면 `proxy.ts`는 실행조차 안 된다. 진짜 방어는 ③의 RLS다.

(Next 16부터 파일 이름이 `middleware.ts` → `proxy.ts`로 바뀌었다. 예전 이름도 되지만 경고가 뜬다.)

# 4. React 기초 — 화면과 값이 같이 움직이는 법

## 4-1. state

**없으면 뭐가 불편한가.**

```js
let posting = false;
function onClick() {
  posting = true;   // 값은 바뀐다
}
```

값은 바뀌는데 **화면은 그대로다.** React는 이 변수를 쳐다보고 있지 않으니까.

**그래서 state가 뭔가.**
"값이 바뀌면 화면을 다시 그려야 하는 것"을 담는 상자.

```tsx
const [posting, setPosting] = useState(false);
//     ↑현재값   ↑바꾸는 함수      ↑처음 값
```

`setPosting(true)`를 부르면 React가 "아 값이 바뀌었네" 하고 **이 함수를 처음부터 다시 실행해서** 화면을 새로 그린다.

**핵심**: state는 **그 탭의 메모리**다. 새로고침하면 사라진다. 다른 탭은 모른다.

우리가 실험으로 본 것: `/map`을 탭 두 개에 열고 한쪽에서 로그아웃하면, 다른 탭의 📸 버튼이 그대로 남아 있었다. `signedIn`이라는 state가 그 탭 안에서만 살기 때문.

## 4-2. useEffect

**없으면 뭐가 불편한가.**
지도를 그리려면 `<div>`가 화면에 실제로 존재해야 한다. 그런데 컴포넌트 함수가 실행되는 시점엔 아직 없다(React가 아직 화면에 안 붙였으니까).

**그래서 이건 뭔가.**
"화면이 실제로 그려진 **다음에** 이걸 실행해줘"라고 예약하는 것.

```tsx
useEffect(() => {
  // 여기는 화면이 그려진 뒤에 실행된다
}, []);
//  ↑ 이 대괄호가 "언제 다시 실행할지"를 정한다
```

| 두 번째 인자 | 언제 실행되나 |
|---|---|
| `[]` (빈 배열) | **딱 한 번**, 페이지가 처음 뜰 때만 |
| `[coords]` | 처음 한 번 + `coords`가 바뀔 때마다 |
| 없음 | 화면을 다시 그릴 때마다 (거의 안 씀) |

**우리가 이걸로 걸린 적**: 인앱 브라우저 배너를 테스트하려고 개발자도구에서 UserAgent를 바꿨는데 배너가 안 떴다. `[]`라서 **페이지가 처음 뜰 때 딱 한 번** UA를 읽고 끝났기 때문. 새로고침하니까 떴다. 

그리고 `useEffect`가 **함수를 돌려주면** 그건 "떠날 때 실행할 뒷정리"가 된다:

```tsx
useEffect(() => {
  const channel = supabase.channel(...).subscribe();
  return () => supabase.removeChannel(channel);  // ← 페이지 떠날 때
}, []);
```

안 치우면 페이지를 오갈 때마다 연결이 쌓인다.

## 4-3. useRef

**state와 뭐가 다른가.**

|  | 바뀌면 화면 다시 그림? | 새로고침하면? |
|---|---|---|
| `useState` | **그림** | 사라짐 |
| `useRef` | 안 그림 | 사라짐 |

캔버스 요소 같은 건 붙잡아 두기만 하면 되고 바뀐다고 화면을 다시 그릴 필요가 없다. 그래서 `canvasRef`, `mapRef`는 `useRef`다.

# 5. ③ Supabase 안에 뭐가 들었나

Supabase는 **네 가지를 한 덩어리로 파는 서비스**다. 하나씩 본다.

## 5-1. Postgres — 데이터베이스

**없으면 뭐가 불편한가.**
게시물 정보를 어디 적어둬야 한다. 파일에 적으면? 두 사람이 동시에 쓰면 깨지고, "이 유저가 오늘 몇 장 올렸나"를 세려면 파일 전체를 읽어야 한다.

**그래서 데이터베이스가 뭔가.**
표(table)를 잘 관리해주는 프로그램. 엑셀 시트라고 생각하면 거의 맞다. 다만 훨씬 빠르고, 여러 사람이 동시에 써도 안 깨지고, "조건에 맞는 것만 뽑아줘"를 잘한다.

**Postgres**는 그 데이터베이스 프로그램 중 하나의 이름이다(가장 널리 쓰이는 것 중 하나).

우리 `posts` 표는 이렇게 생겼다:

| id | user_id | photo_url | lat | lng | created_at |
|---|---|---|---|---|---|
| a3f… | 7b2… | https://…/abc.jpg | 40.5012 | -74.4487 | 2026-08-04 21:04 |
| c91… | 7b2… | https://…/def.jpg | 40.4998 | -74.4501 | 2026-08-04 21:31 |

- **행(row)** = 가로 한 줄 = 게시물 하나
- **열(column)** = 세로 한 칸 = "모든 게시물이 갖는 항목"

**SQL** = 데이터베이스에게 시키는 말. 영어랑 비슷하게 생겼다.

```sql
select id, lat, lng from posts;      -- posts에서 이 세 칸만 다 가져와
insert into posts (...) values (...); -- 새 행 하나 추가
delete from posts;                    -- 다 지워
```

`supabase/migrations/` 안의 `.sql` 파일들이 전부 이 말들이다.

**마이그레이션(migration)이 뭔가.**
데이터베이스 구조를 바꾼 기록. `20260728000000_posts_table_and_rls.sql` 같은 파일 하나가 "이때 이런 변경을 했다"는 뜻이다. 앞의 숫자는 날짜라 **순서대로 실행하면 빈 데이터베이스가 지금 상태가 된다.**

## 5-2. 버킷 (Storage) ★

여기가 네가 모르겠다고 한 부분이다. 천천히.

**없으면 뭐가 불편한가.**

사진을 데이터베이스 표 안에 넣으면 안 되나? 넣을 수는 있다. 그런데:

- 사진 한 장이 **300KB~3MB**다. 글자 몇 개짜리 행 옆에 이런 덩어리가 들어가면 표가 순식간에 뚱뚱해진다
- 데이터베이스는 "조건에 맞는 행 찾기"를 잘하려고 만든 물건이다. 큰 덩어리를 통째로 꺼내주는 건 잘 못한다
- 브라우저의 `<img src="...">`는 **주소**를 원한다. 데이터베이스 안에 있으면 그 주소를 만들 수가 없다

**그래서 Storage가 뭔가.**

**인터넷에 있는 파일 창고.** 파일을 넣어두면 각 파일마다 주소가 생긴다. 그 주소를 `<img src>`에 넣으면 사진이 보인다.

**그럼 버킷(bucket)은 뭔가.**

**창고 안의 방 하나.** 영어로 "양동이"인데 뜻은 "구분된 큰 통"에 가깝다. 파일들을 성격별로 나눠 담는 최상위 구분이다.

```
Storage (창고 건물)
├── 📦 photos   버킷   ← 오늘 올라온 사진들. 아무나 볼 수 있음
│     ├── 7b2c.../abc.jpg
│     ├── 7b2c.../def.jpg
│     └── 9f1a.../ghi.jpg
└── 📦 archive  버킷   ← 06시에 옮겨진 옛날 사진들. 아무도 못 봄
      └── 7b2c.../old.jpg
```

**왜 방을 나누나.** 방마다 **규칙을 따로 걸 수 있기 때문**이다.

- `photos` = **public**. 주소만 알면 누구나 볼 수 있다
- `archive` = **private**. 로그인해도 못 본다(정책이 하나도 없어서 아무도 통과 못 함)

**왜 `photos`가 public인가.**
`/map`은 로그인 안 해도 볼 수 있는 화면이다. 거기서 사진이 `<img src>`로 그냥 열려야 한다. private으로 하면 사진마다 "1시간짜리 임시 통행증 주소"를 발급받아야 하는데, 핀이 50개면 발급 요청이 50번이다.

**버킷 안의 폴더 구조.**

파일 경로를 `<유저id>/<랜덤이름>.jpg` 로 정했다:

```ts
const path = `${user.id}/${crypto.randomUUID()}.jpg`;
```

이게 그냥 정리정돈이 아니라 **권한 규칙 그 자체**다. 버킷 정책이 이렇게 돼 있다:

> "올리려는 경로의 **첫 번째 칸**이, 요청에 딸려온 토큰에서 꺼낸 **진짜 네 id**와 같아야 통과"

그래서 폴더를 가졌다는 게 곧 파일을 가졌다는 뜻이 되고, 남의 사진을 덮어쓸 방법이 없다. 소유권 표를 따로 만들 필요가 없어진다.

**꼭 기억할 것: 표의 행과 창고의 파일은 서로 모른다.**

`posts` 행의 `photo_url`은 그냥 **글자**다. "이 주소에 사진이 있다"고 적혀 있을 뿐, 실제 파일과 연결된 끈이 아니다.

```sql
delete from posts;   -- 행은 사라짐
```
이래도 **사진 파일은 창고에 그대로 남는다.** 아무도 안 가리키는 파일 = orphan(고아).

파일을 진짜로 옮기거나 지우려면 **Storage에 HTTP 요청을 따로 보내야 한다.** 이게 06시 리셋이 복잡했던 이유다(9장에서 다시).

## 5-3. RLS — 진짜 방어선

**없으면 뭐가 불편한가.**

`posts` 표를 아무나 읽고 쓸 수 있으면, 학생이 개발자도구를 열고

```js
supabase.from("posts").delete()
```

한 줄로 오늘 올라온 사진을 전부 지울 수 있다. 우리 서버 코드가 뭐라고 적혀 있든 상관없다. **①이 ②를 건너뛰니까.**

**그래서 RLS가 뭔가.**

**Row Level Security = 행 단위 보안.** 표 앞에 경비원을 세우고 "이 요청이 이 행을 만져도 되나?"를 **데이터베이스가 직접** 판단하게 하는 것.

우리 정책 세 개:

```sql
-- ① 읽기: 누구나 (로그인 안 해도)
create policy "posts are publicly readable"
  on public.posts for select
  using (true);

-- ② 쓰기: 로그인했고 + 본인 id로 쓰고 + 오늘 3장 안 넘었을 것
create policy "authenticated users can post within rules"
  on public.posts for insert to authenticated
  with check (auth.uid() = user_id and public.can_post(auth.uid()));
```

**`using` vs `with check`** — 헷갈리는 지점이다.

| | 언제 쓰나 | 무엇을 검사하나 |
|---|---|---|
| `using` | SELECT / DELETE / UPDATE | **이미 있는 행**을 봐도 되나 |
| `with check` | INSERT / UPDATE | **새로 넣으려는 값**이 규칙에 맞나 |

읽기는 "이 행 봐도 돼?"니까 `using`. 쓰기는 "이 값 넣어도 돼?"니까 `with check`.

**`auth.uid()`가 뭔가.**

"지금 이 요청을 보낸 사람의 진짜 id". 클라이언트가 보낸 값이 아니라 **Supabase가 토큰을 검증해서 직접 꺼낸 값**이다. 그래서 클라이언트가 `user_id`에 남의 id를 적어 보내면 `auth.uid() = user_id`에서 걸린다.

**3장 제한도 여기 있다.**

```sql
create function public.can_post(uid uuid) returns boolean ...
  select (오늘 06시 이후 이 유저의 게시물 수) < 3
```

시간을 **데이터베이스의 시계**로 잰다. 클라이언트가 폰 시계를 조작해도 소용없다.

**거절당하면 뭐가 오나.** `42501` — Postgres의 "권한 없음" 코드. 사람이 읽을 수 없는 말이라 `/capture`에서 문장으로 바꿔준다:

```ts
code === "42501"
  ? "You've hit today's limit of 3 photos. Comes back at 6 AM."
  : ...
```

## 5-4. Auth — 로그인

**없으면 뭐가 불편한가.**
"이 요청 보낸 사람이 누구인지"를 모르면 3장 제한도 폴더 규칙도 못 건다.

**우리 방식: 6자리 코드(OTP).**

1. 학생이 NetID를 입력 → Supabase가 그 주소로 6자리 숫자를 메일 발송
2. 학생이 그 숫자를 **지금 보고 있는 화면에** 입력
3. 맞으면 Supabase가 이 브라우저에 **세션 쿠키**를 심어준다 = 로그인 완료

**왜 매직 링크(누르면 바로 로그인되는 링크)를 버렸나.**

매직 링크는 **메일 앱이 링크를 여는 브라우저에** 로그인을 심는다. Gmail 앱은 링크를 구글 인앱 브라우저로 연다. 그런데 로그인 상태(쿠키)는 **브라우저마다 따로** 저장된다.

→ 학생은 구글 인앱 브라우저에서 로그인됨 → 나중에 사파리로 앱을 열면 **로그아웃 상태**.

안내문으로 못 덮는 구조적 문제다. 숫자 코드는 학생이 **눈으로 읽어서** 원래 화면에 치기 때문에 브라우저를 건너가지 않는다.

**세션 토큰이 실제로 뭐냐.**

쿠키 안에 든 그 긴 문자열. 개발자도구 콘솔에서 `document.cookie` 치면 보인다.

- **해시가 아니다.** 해시는 되돌릴 수 없는 것(비밀번호 저장용). 이건 **인코딩** — 그냥 다른 글자로 바꿔 적은 것이라 누구나 읽을 수 있다
- **JWT** 형식이면 점(`.`)으로 세 조각: `머리.내용.서명`
- 내용에는 네 id, 이메일, 만료 시각이 들어 있다. 다 읽힌다
- **위조가 안 되는 이유는 세 번째 조각(서명)이다.** Supabase만 아는 비밀로 계산한 값이라, 내용을 한 글자라도 고치면 서명이 안 맞는다

그래서 `getSession()`이 **네트워크 없이** 로그인 여부를 알 수 있다 — 쿠키를 해독하기만 하면 되니까. `/map`이 이걸 쓴다.

## 5-5. Realtime — 실시간

**없으면 뭐가 불편한가.**
누가 사진을 올려도 지도를 보고 있는 사람은 새로고침해야 보인다.

**폴링(polling)이라는 방법이 있다.** 3초마다 "새 거 있어?"라고 물어보는 것. 문제는 **비용이 사람 수 × 빈도**로 늘어난다는 것. 새벽 4시에 100명이 지도를 켜놓고 있으면 아무 일도 없는데 초당 33번 물어본다.

**그래서 Realtime이 뭔가.**

**연결을 하나 열어두고 서버가 알려주는 방식**(웹소켓). 조용할 땐 통신량이 0이고, 새 행이 생긴 순간에만 그 행이 밀려온다.

```ts
supabase
  .channel("posts-inserts")
  .on("postgres_changes", { event: "INSERT", table: "posts" }, (payload) => {
    addMarker(map, payload.new);   // ← 밀려온 새 행
  })
  .subscribe();
```

**여기서 배운 함정이 크다.**

`.subscribe()`가 `SUBSCRIBED`를 돌려주는데도 데이터가 안 왔다. 이유:

- **구독 등록**은 Realtime 서버가 받는다 → "등록됐어"(SUBSCRIBED)
- **데이터 공급**은 Postgres가 한다 → `posts` 표를 `supabase_realtime` **publication**에 넣어줘야 흘려보낸다

둘이 **별개 계층**이다. 신문 구독 신청서는 접수됐는데 신문사가 그 신문을 안 찍고 있는 상태.

# 6. 저장 장소 3개

같은 "저장"인데 규칙이 완전히 다르다. 이게 여러 버그의 뿌리였다.

| | 어디까지 살아남나 | ②Next 서버가 볼 수 있나 |
|---|---|---|
| **React state** (`signedIn`, `coords`) | 그 탭, 새로고침하면 사라짐 | ❌ |
| **쿠키** (Supabase 세션) | 브라우저 전체, 탭 닫아도 남음 | ✅ **요청마다 자동으로 딸려감** |
| **localStorage** (배너 접기) | 브라우저 전체, 탭 닫아도 남음 | ❌ **절대 안 감** |

**마지막 칸이 전부를 설명한다.**

- 로그인은 **쿠키**여야 한다 → `proxy.ts`(②)가 읽어야 `/capture`를 막을 수 있으니까
- 배너 접기는 **localStorage**면 된다 → 서버가 알 필요가 없다. 쿠키에 넣으면 요청마다 쓸데없이 실려 간다

**`@supabase/ssr` 패키지를 깐 이유가 이거다.** 기본 `supabase-js`는 세션을 localStorage에 저장한다 → 그러면 브라우저는 로그인 상태를 아는데 **서버는 영원히 모른다** → `proxy.ts`가 원천적으로 불가능해진다. `@supabase/ssr`이 하는 일의 핵심은 **저장 위치를 localStorage → 쿠키로 바꾸는 것**이다.

# 7. 키 — 왜 공개해도 되는가

우리 앱에 키가 세 개 있고 **전부 브라우저에 그대로 박혀 있다.**

```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY      = sb_publishable_...
NEXT_PUBLIC_MAPBOX_ACCESS_TOKEN    = pk....
```

**`NEXT_PUBLIC_` 접두사가 뭔가.**

"공개해도 된다"는 허가가 아니라 **빌드할 때 이 값을 브라우저 자바스크립트에 글자 그대로 박아 넣으라는 명령**이다. 그래서:

- 브라우저에서 볼 수 있어야 하는 값만 이 이름을 붙인다
- Mapbox 토큰에 시크릿 권한을 하나라도 켜면 그 권한이 전 세계에 뿌려진다
- 값을 바꾸면 **다시 빌드해야** 반영된다(서버 재시작으론 안 됨). 이미 박혀버렸으니까

**그럼 왜 안전한가.**

키는 **이름표**지 통행증이 아니다. 진짜 방어선은 따로 있다.

| 키 | 진짜 방어선 |
|---|---|
| Supabase publishable | **RLS** — 키가 있어도 정책이 거절하면 끝 |
| Mapbox `pk.` | **URL 제한** — 우리 도메인이 아닌 곳에서 오면 403 |

Mapbox 제한은 눈으로 확인했다:

```
Referer: https://ru-vibe.vercel.app/   → 200
Referer: https://evil.example.com/     → 403 Forbidden
```

**반대로 절대 브라우저에 두면 안 되는 키**: `service_role`(구형) / `sb_secret_`(신형). 이건 **RLS를 통째로 무시한다.** 방어선이 없다 — 그게 존재 이유니까. 그래서 이 키는 Supabase의 **Vault**(금고)에 넣어두고 데이터베이스 안에서만 꺼내 쓴다.

**신형 키의 함정 하나** — `sb_secret_`은 점이 0개다. **JWT가 아니다.**

| 헤더 | 받는 것 |
|---|---|
| `Authorization: Bearer` | **JWT** — 서명을 계산해서 검증 |
| `apikey` | **API 키** — 목록에서 찾아봄 |

신형 키를 `Authorization`에 넣으면 Storage가 세 조각으로 쪼개려다 실패하고 `400 Invalid Compact JWS`("세 조각짜리를 기대했다")를 뱉는다. **키가 틀린 게 아니라 줄을 잘못 선 것**이라 증상만 보면 원인이 안 보인다.

# 8. 사진 한 장이 올라가는 전 과정

여기까지 나온 걸 전부 꿰는 이야기다. **면접에서 이 프로젝트를 설명할 때 이 순서로 하면 된다.**

### ① 학생이 `/capture`를 연다

브라우저 → **`proxy.ts`(②)** → 쿠키를 보고 로그인 확인 → 통과 or `/login`으로 307

### ② 사진을 찍는다 (①에서 전부)

`<input type="file" capture="environment">` → **아이폰 기본 카메라 앱**이 열린다.

> 왜 커스텀 뷰파인더(`getUserMedia`)를 안 쓰나: 플래시·야간모드·손떨림보정을 다 포기해야 하고 iOS 삽질이 많다. 대신 라이브 화면 위에 UI를 못 얹는데, 우리는 어차피 찍은 뒤에 캔버스에서 합성하니까 상관없다.

`PolaroidCanvas`가 캔버스에 그린다:
1. 실물 폴라로이드 스캔 사진(`public/frame.jpg`)을 깔고
2. 흰 창 안에 사진을 정사각형으로 오려 넣고
3. 필름 색감을 입히고(합성모드 4단계 + 그레인 2겹)
4. GPS가 도착하면 아래 여백에 위치·날짜·시간을 적는다

> 캔버스 긴 변을 제한하는 이유: iOS 사파리는 캔버스가 너무 크면 **에러 없이 빈 이미지**를 내놓는다. 48MP 아이폰 사진이 여기 걸린다.

### ③ GPS를 받는다 (①)

```ts
navigator.geolocation.getCurrentPosition(성공콜백, 실패콜백, 옵션)
```

즉시 답이 안 나오므로 "결과를 돌려주는 함수"가 아니라 **"다 되면 이 함수를 불러줘"** 형태다(= 콜백).

> 인스타·Gmail 인앱 브라우저에서는 이게 **조용히 죽는다.** 권한 팝업도 안 뜨고 콜백 둘 다 안 불려서 `locating…`에 영원히 멈춘다. 카메라는 되는데 GPS만 죽어서 원인이 안 보인다. 그래서 배너로 "사파리로 여세요"를 띄운다.

### ④ Post를 누른다 (① → ③ 직통, ②는 관여 안 함)

```
캔버스 → JPEG 덩어리(Blob)
      → Storage의 photos 버킷에 <내id>/<랜덤>.jpg 로 업로드
         └ 버킷 정책이 "첫 칸 == 토큰 속 진짜 내 id"인지 검사
      → 그 파일의 public 주소를 문자열로 조립 (네트워크 요청 아님)
      → posts 표에 행 1개 INSERT
         └ RLS가 auth.uid() 일치 + 오늘 3장 이하인지 검사
```

거절되면 `42501`이 오고, 화면에 사람 말로 바꿔 보여준다.

### ⑤ 지도에 나타난다 (③ → 다른 사람들의 ①)

INSERT가 성공한 순간 Postgres가 그 행을 publication에 흘리고 → Realtime 서버가 구독자들에게 밀어주고 → 각자의 브라우저에서 `addMarker()`가 돌아 핀이 생긴다. **아무도 새로고침하지 않았는데.**

# 9. 06시 리셋 — 아무도 안 보는데 돌아가는 코드

**없으면 뭐가 불편한가.**
"오늘 밤"만 보여주는 앱인데 어제 사진이 계속 쌓여 있으면 컨셉이 죽는다.

**누가 실행하나.** 유저가 앱을 안 켜도 돌아야 한다. 그래서 **스스로 깨어나는 주체**가 필요하다.

**pg_cron** — Postgres 안에 든 알람시계. "매시 정각에 이 함수를 불러라"를 등록해둔다.

```
0 * * * *     ← 매시 0분
```

**왜 `0 10 * * *`(UTC 10시 = 뉴욕 6시)로 안 박았나.**

뉴욕은 서머타임 때문에 UTC와의 차이가 **1년에 두 번 바뀐다**(여름 -4시간, 겨울 -5시간). UTC 시각을 박아두면 11월 어느 날부터 **에러 하나 없이** 1시간 어긋난다. 그래서 매시 깨어나되, **06시인지는 함수 안에서 뉴욕 시각으로** 판단한다.

```sql
if extract(hour from (now() at time zone 'America/New_York')) <> 6 then
  return;   -- 하루 23번은 이것만 보고 돌아간다. 비용은 사실상 0
end if;
```

**함수가 하는 일 두 가지.**

**(가) 행 옮기기 — 쉽다.** 그냥 SQL이다.
```sql
insert into public.posts_archive select * from public.posts;
delete from public.posts;
```

**(나) 파일 옮기기 — 여기가 어렵다.**

5-2에서 본 것: **행을 지워도 파일은 안 지워진다.** `photo_url`은 그냥 글자니까. 파일을 진짜 움직이려면 **Storage에 HTTP 요청**을 보내야 한다.

그런데 Postgres는 원래 HTTP를 못 쏜다. 그래서 **pg_net**이라는 확장을 켠다.

```sql
perform net.http_post(
  url := '.../storage/v1/object/move',
  headers := jsonb_build_object('apikey', key),
  body := jsonb_build_object('bucketId','photos','sourceKey',o.name, ...)
)
from storage.objects o where o.bucket_id = 'photos';
```

**여기 제일 큰 함정: `net.http_post`는 비동기다.**

요청 번호만 즉시 돌려주고 **실제 응답은 나중에** `net._http_response` 표에 도착한다. 그래서 **실패해도 그 자리에서 에러가 안 난다.** 확인하려면 따로 봐야 한다:

```sql
select status_code, content, created from net._http_response
order by created desc limit 5;
```

> `created`는 **UTC**다. 뉴욕 시각으로 환산해서 "이게 방금 것인지"를 봐야 한다. 옛날 성공 응답을 보고 "잘 됐네" 하고 넘어가기 딱 좋다.

**왜 Edge Function을 안 썼나.**

하는 일이 "파일 옮기고 행 옮기고 지우기"뿐인데, Edge Function을 쓰면 Deno 런타임 + 배포 파이프라인 + **그걸 깨울 cron** + cron이 쓸 키가 전부 따라온다. cron은 어차피 필요하니까 pg_cron 하나로 끝내는 게 부품이 적다.

**보안 한 줄.** 새로 만든 함수는 Postgres 기본이 **"누구나 실행 가능"**이다. 안 막으면 아무나 RPC로 `reset_daily()`를 불러서 앱을 통째로 비울 수 있다.

```sql
revoke execute on function public.reset_daily() from public, anon, authenticated;
```

# 10. 배포

**빌드(build)가 뭔가.**

우리가 쓴 TypeScript·JSX는 브라우저가 못 읽는다. 브라우저가 읽는 자바스크립트로 **번역하고 한 덩어리로 묶는** 과정이 빌드다. `bun run build`.

이때 `NEXT_PUBLIC_*` 값들이 **글자 그대로 박힌다.** 그래서 값을 바꾸면 다시 빌드해야 한다.

**Vercel이 하는 일.**

GitHub 레포와 연결해두면, `git push` → Vercel이 코드를 받아 → 빌드 → 자기 서버에 올림 → 주소로 접속 가능. 자동이다.

**환경변수를 Vercel에 또 넣어야 하는 이유.**

`.env.local`은 `.gitignore`에 걸려 있어서 **GitHub에 안 올라간다**(키를 공개 레포에 올리면 안 되니까). Vercel은 코드를 GitHub에서 받아오므로 그 파일이 없다. 그래서 같은 값을 Vercel에 따로 알려줘야 한다.

**PWA가 뭔가.**

Progressive Web App — **웹사이트인데 홈 화면에 아이콘으로 설치되고, 열면 주소창 없이 앱처럼 뜨는 것.** 앱스토어를 안 거친다.

설치되려면 네 가지가 필요하다:

| | 우리 파일 |
|---|---|
| manifest (앱 이름·색·시작 주소) | `app/manifest.ts` |
| 아이콘 | `public/icon-{192,512}.png`, `app/apple-icon.png` |
| service worker | `public/sw.js` |
| **HTTPS** | 배포하면 자동 (localhost는 예외로 봐줌) |

**service worker가 뭔가.** 페이지와 별개로 백그라운드에 상주하면서 이 사이트의 요청에 끼어들 수 있는 스크립트. 원래는 오프라인 캐시용인데, **우리는 캐시를 안 한다** — 이 앱 화면은 전부 "지금" 데이터라 캐시된 화면은 느린 화면보다 나쁘다. `fetch` 핸들러가 **존재한다는 사실 자체**가 크롬의 설치 조건이라 껍데기만 둔 것이다.

**아이폰만 다르다.** 안드로이드/데스크톱 크롬은 주소창에 설치 아이콘을 알아서 띄우는데, **아이폰은 설치 프롬프트가 아예 없다.** 유저가 공유 버튼 → "홈 화면에 추가"를 직접 눌러야 하고, 웹페이지가 그걸 코드로 실행하는 건 iOS가 금지한다. 그래서 우리가 할 수 있는 건 **말로 알려주는 것**뿐이다.

# 11. 반복해서 나온 패턴 — 디버깅 감각

이 프로젝트에서 같은 모양의 사고를 여러 번 겪었다. 이게 제일 값진 부분이다.

## 패턴 1. "안 된다"의 원인이 설정이 아니라 **내가 엉뚱한 곳을 재고 있었던 것**

세 번 나왔다:

1. `apple-touch-icon`이 HTML에 있을 리 없다고 예상 → 있었다. Next가 **파일 이름만 보고** 자동으로 넣어줬으니까
2. UserAgent를 바꿨는데 배너가 안 떴다 → **새로고침을 안 해서**. `useEffect([])`는 처음 한 번만 돈다
3. Mapbox URL 제한이 안 걸린 것 같았다 → **스타일 JSON 주소**로 쟀기 때문. 제한은 **타일 주소**에 걸린다

**교훈: "설정이 잘못됐나?" 전에 "내가 맞는 문을 두드렸나?"를 먼저 묻는다.**

## 패턴 2. 요청을 보냈다 ≠ 결과가 나왔다 (비동기)

- `net.http_post`는 번호만 주고 끝. 실패해도 그 자리에선 조용하다
- `.subscribe()`는 "등록됐다"만 알려준다. 데이터가 온다는 뜻이 아니다
- `getCurrentPosition`은 즉시 답을 안 준다. 콜백을 맡기는 것이다

**교훈: 비동기 작업은 "보냈다"와 "됐다"를 따로 확인해야 한다.**

## 패턴 3. 어느 계층에서 막혔는지가 정보다

없는 파일을 옮기라고 시켜서 인증만 검사한 방법:

| 답변 | 어디서 막혔나 |
|---|---|
| `Invalid Compact JWS` | **문 앞** — 키를 안 받아줌 |
| `NoSuchKey` | **문 통과** — 안에서 파일을 찾다가 없었음 |

**일부러 실패시키되, 내가 보고 싶은 관문보다 *뒤에서* 실패하게 만든다.** 그러면 에러 메시지가 "어디까지 갔는지" 재는 자가 된다.

## 패턴 4. 개입 계층 — 우리가 안 불렀는데 자동으로 끼어드는 것들

| 무엇 | 어디(장소) | 언제 |
|---|---|---|
| `proxy.ts` | ② | 요청이 페이지에 닿기 전 |
| `posts` RLS | ③ | 모든 SELECT/INSERT 때 |
| Storage 버킷 정책 | ③ | 모든 업로드 때 |
| `supabase_realtime` publication | ③ | 행이 바뀔 때 |
| 브라우저의 쿠키 자동 첨부 | ① | 모든 요청 때 |
| Next의 파일 이름 규칙 | ② | 빌드할 때 |

**공통점: 우리 코드에 "이걸 불러라"라고 적힌 곳이 없다.** 그래서 코드만 읽으면 안 보인다. 이게 네가 어려워하던 부분이고, 이 표가 그 답이다.
